## Question

When one phone plays a Silbo text message and another phone listens, how often does the exact text arrive, and which real-world sound problems break it first?

## Method

**What is tested.** This is the app's own text path, unchanged: `planText()` encodes the message as one MFSK frame (profile 1 «robusto», 10 bits per 24 ms symbol, 984–6563 Hz, Reed-Solomon with 48 parity bytes, CRC-32). The audio goes through a simulated acoustic channel, and the app's `decodeWindow()` decodes it. A message counts as delivered only if the decoded text is exactly the text that was sent. `bench/CODEC.md` describes the codec.

**The channel.** `bench/channel/` has ten impairments, each with one strength setting and its own seeded random stream. They are applied in physical order: speaker nonlinearity → distance → room reverb → café babble → cheap microphone → clock drift / start offset → white noise floor → input clipping → dropouts → 16-bit quantisation. Every condition includes a quiet-room noise floor (30 dB in-band SNR at 1 m), a random 0.2–1.0 s lead before the message and a random fractional-sample delay. All noise is synthesised; no recordings are used. Each impairment has a unit test that checks it does what its name says (`bench/test/channel.test.ts`). For example, the reverb test checks the requested RT60 and direct-to-reverberant ratio, and the drift test checks the requested ppm.

**The experiments.** Each impairment is swept on its own from harmless to destructive, with 200 random messages per step. Messages are 16, 64 or 140 characters long in rotation, drawn from an alphabet with accents and punctuation. There are also three combined scenarios (quiet office, café table, worst realistic case), and 10 minutes per noise type of message-free audio to count false messages. Each step's seed is fixed, so two codec versions are tested on exactly the same sound. Every rate comes with a 95 % Wilson interval. Besides the pass/fail rate, the bench records:

- the character error rate;
- whether the preamble was found within 10 ms of where it really is;
- the raw bit error rate of the tones before error correction, measured with perfect timing.

The raw bit error rate shows how close a step is to failing even while every message still gets through. The ablations (`bench/ablations.ts`) re-run selected conditions with a single change, on the same sound:

- a receiver-side change to the captured buffer;
- one impairment removed from a scenario;
- an alternative MFSK profile, sent through the codec's own experiment hook.

The app is never changed.

## Findings

Ranked by impact: how much of real use each one plausibly affects, multiplied by how badly it fails. Numbers are from the full run (200 messages per step); `key = value` marks the exact figure in `bench/results/`.

1. **Room echo is the main way messages are lost, and it isn't close.** In the three everyday scenarios, the success rate is `scenario.quiet.rate = 88.5%` (quiet office, 1 m), `scenario.cafe.rate = 21.5%` (café table, 1 m) and `scenario.worst.rate = 0%` (worst realistic case). Taking only the reverb out of the same sound restores nearly everything: `ablation.loo-worst.no-rt60.app.rate = 99.5%`, `ablation.loo-cafe.no-rt60.app.rate = 100%`, `ablation.loo-quiet.no-rt60.app.rate = 100%`. Taking out the café babble, the cheap microphone, clock drift, clipping or dropouts changes almost nothing (`ablation.loo-cafe.no-babbleDb.app.rate = 23%`). What matters is how far apart the phones are compared with the room's critical distance (about 0.5–1 m in a 100 m³ room). Moving the worst case's phones from 2 m to 0.5 m alone gives `ablation.loo-worst.no-distanceM.app.rate = 98.5%`. With the phones 0.5 m apart, the reverb sweep holds 90 % up to RT60 `reverb.limit90 = 1.70` s. In the worst case the echo is so strong that even the preamble is rarely found (`scenario.worst.syncRate = 1%`, raw bit errors `scenario.worst.rawBer = 25.6%`).
2. **Long messages fail first, under every impairment.** Each Reed-Solomon codeword gets a fixed 48 parity bytes, whatever the message length. A 16-character text is about 70 % parity, while a 140-character text is about 25 %. At the white-noise cliff, `awgn[-7].len16 = 95.5%` of short messages arrive but `awgn[-7].len140 = 0%` of long ones. At the café table the split is `scenario.cafe.len16 = 59.7%` against `scenario.cafe.len140 = 0%`, and in the quiet office `scenario.quiet.len140 = 71.2%` of long texts arrive. The same pattern repeats at the edge of every sweep.
3. **Starting to listen even 1 ms late loses the message.** If the receiver starts recording after the 85 ms preamble has begun, decoding fails: `late[1].rate = 0%`, and the same holds for every lateness tested up to `late[80].rate = 0%`. The preamble correlator cannot match a chirp that begins before sample 0, even though the rest of the frame is intact. This only bites when listening starts inside that 85 ms window, so it affects few messages, but when it happens the loss is total and needless.
4. **Noise alone is not the problem.** The decoder works down to an in-band SNR of `awgn.limit90 = -6.2` dB in white noise and `babble.limit90 = -17.5` dB in café babble. Those are far below what a phone 1 m away produces in a noisy café, where the scenario puts the babble 5 dB *below* the signal. In the free field (no room), distance only matters through the noise floor: `distance.limit90 = 24.5` m.
5. **Bad hardware barely matters.** A microphone has to cut off below `mic.limit90 = 1974` Hz before messages fail; a typical cheap 4 kHz microphone gives `mic[4000].rate = 100%`. Speaker saturation and input clipping up to 40 dB are harmless (`speaker[40].rate = 100%`, `clip[40].rate = 100%`), because tone detection ignores amplitude. Clock drift is tolerated up to `drift.limit90 = 2292` ppm, ten times worse than real phones (`drift[2000].rate = 100%`).
6. **Audio glitches are tolerated at realistic rates.** One 5–40 ms dropout per second costs nothing (`dropouts[1].rate = 100%`). The 90 % limit is at `dropouts.limit90 = 5.9` gaps per second, far more than a working phone produces.
7. **No false messages and no wrong text.** Ten minutes each of white noise, café babble and the worst-case chain without a signal produced `false.white.frames = 0`, `false.babble.frames = 0` and `false.worst.frames = 0` messages. The preamble detector fired at most `false.worst.alarms = 1` time per ten minutes, and each such alarm costs only a header decode. Across all 16,800 trials of the full run the CRC-32 never let a wrong text through: a message either arrives exactly or not at all.

## Suggestions

Ranked by evidence per unit of cost. None is implemented on this branch; suggestion 1 is implemented and measured on `bench/improve-late-start` (see `bench/IMPROVE.md`).

1. **Put one preamble of silence in front of every receive window** (receiver only: no change to the sound or the wire format, no extra airtime). Measured on the same sound, a capture that starts 1 to 80 ms into the preamble goes from `late[80].rate = 0%` to `ablation.pad.80.pad.rate = 100%` (and `ablation.pad.1.pad.rate = 100%`). Cost: 85 ms more audio to scan per decode.
2. **Fight the echo with more hop sets rather than more parity.** A profile with one more hop set (H = 7) means echoes of the last six symbols land outside the bins being compared. It costs no airtime, and on the same sound it lifts RT60 2 s at 0.5 m from `ablation.profiles.reverb-2.robusto.rate = 78%` to `ablation.profiles.reverb-2.hops-7.rate = 97%`, the café table from `ablation.profiles.cafe.robusto.rate = 19.5%` to `ablation.profiles.cafe.hops-7.rate = 36.5%` and the quiet office from `ablation.profiles.quiet.robusto.rate = 88%` to `ablation.profiles.quiet.hops-7.rate = 94.5%`. Its catch is that the highest tone moves up to ~7.5 kHz, so a microphone cut off at 2 kHz drops from `ablation.profiles.mic-2000.robusto.rate = 92.5%` to `ablation.profiles.mic-2000.hops-7.rate = 65.5%`. Some phone microphones roll off well below 7.5 kHz, so test this on real phones first. A slower variant (8 bits/symbol, H = 7, +20 % airtime) gets most of the gain without that catch: `ablation.profiles.cafe.slow-8bit.rate = 39.5%` and `ablation.profiles.mic-1750.slow-8bit.rate = 88.5%`. Either is a wire-format change and needs a new profile id. Neither rescues the worst case (`ablation.profiles.worst.hops-7.rate = 0%`): at 2 m in a live room the fix is to tell users to bring the phones closer. A hint in the app when the preamble is found but decoding fails would do that.
3. **Scale the error-correction parity with message length.** Long texts are the first to fail (finding 2), because a fixed 48 parity bytes is a thinner shield on 150 bytes than on 20. A third more parity (64 bytes) lifts the quiet office from `ablation.profiles.quiet.robusto.rate = 88%` to `ablation.profiles.quiet.parity-64.rate = 97%`, and 10 dropouts/s from `ablation.profiles.dropouts-10.robusto.rate = 53.5%` to `ablation.profiles.dropouts-10.parity-64.rate = 69.5%`. On average it costs 10 % more airtime. Making the parity proportional to length (for example, never less than half the data bytes) would spend that airtime only on the long texts that need it.

## Limitations

- **It is a simulation.** No real phone, speaker, microphone or room was used. The models are standard textbook models (Sabine reverberation with an exponentially decaying noise tail, 1/d spreading, Butterworth band-limits, `tanh` saturation, Poisson dropouts). The unit tests check that each model does what it says, but not that it matches any particular phone. In particular:
  - Real phone speakers are directional and roll off steeply below ~500 Hz.
  - Real microphones apply automatic gain control and noise suppression, which this channel does not model. Noise suppression is designed to remove steady tones and could be worse than anything simulated here. The app asks the browser to turn it off, but some phones ignore that.
- **Distance high-frequency loss is an assumption** (a low-pass at 16 kHz/√d). Path loss against the fixed noise floor dominates anyway, so the distance limit mostly restates the white-noise limit in metres.
- **The room is one model room.** It has 100 m³ volume and a diffuse tail with no early-reflection pattern. Rooms of a different size or shape, and phones facing away from each other, will differ.
- **Only the text path is measured.** File transfer (OFDM), discreet mode (near-ultrasound) and multi-frame carousels are not swept.
- **The receiver decodes each capture once** instead of replaying the app's 14 s sliding window every 1.5 s. This gives the same pass/fail for a single text frame, but it does not measure the app's real-time CPU budget. Decode times are from Node on a server CPU, not from a phone.
- **Impairments are swept one at a time**, plus three hand-picked combinations. Interactions are only sampled, not mapped.
- **Statistical resolution.** With 200 messages per step, a rate of 100 % means the true rate is at least ~98 % (95 % confidence). Rarer failures than that are invisible. The quick CI run (20 per step) only catches large regressions.
